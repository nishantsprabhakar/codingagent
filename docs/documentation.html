00

Overview

Most AI coding assistants optimize for generating code quickly. Wrexlyn optimizes for verified local outcomes — it plans, edits, runs, checks, and repairs, with a full audit trail, before it tells you a task is done.

It's a single Node.js process with a real desktop-grade web UI (not a browser extension, not a hosted SaaS) that reads and writes files, runs shell commands, and talks to whichever LLM provider you point it at — free ones by default. Everything it touches lives on your machine: sessions, memory, API keys, generated files.

Under the hood, the thing that actually separates it from a chat window with tool access is that nothing it does is taken on the model's word alone. Every mutating action is risk-scored and snapshotted before it runs (§02), code changes are checked against the project's own build/test/lint commands and a second, independent model call before a turn is called done (§02), and generated documents pass a deterministic structural gate before they're written to disk (§12) — so the honesty of the result doesn't hinge entirely on how careful the underlying model happened to be that turn.

It also gets more useful the longer it's used on a given project: preferences stated once are remembered and applied from the very next turn, not just the current one, and multi-step patterns it completes can be saved and recalled rather than re-derived from scratch every session (§13).

The rest of this document walks through what it actually does, screenshot by screenshot, rather than describing it in the abstract.

00A

The product contract

Wrexlyn is not another chat surface. It is a model-independent execution and assurance layer whose job is to convert intent into a controlled, testable and recoverable result.

The underlying model may change by task, price, privacy requirement or customer policy. The operating contract does not: acquire relevant context before mutation; classify and disclose risk; preserve the prior state; execute through governed tools; prefer external checks over self-report; expose uncertainty; and leave enough evidence to inspect or reverse the result.

01Understand before acting

Repository structure, ranked lexical search, extracted symbols and Git history narrow the working set. The agent inspects relevant code instead of inferring an architecture from filenames or a partial prompt.

02Control every mutation

Typed tools, path validation, action-risk classification, explicit permission policy and pre-change snapshots create a visible boundary between model reasoning and effects on the machine.

03Prove completion

Configured builds, tests and lint checks generate a six-state outcome. For non-code deliverables, deterministic structural gates inspect the artifact that will actually be delivered.

04Recover deliberately

Independent critique, bounded repairs, recurrence detection and the Nishant Convergence Protocol replace infinite retries with a finite, evidence-driven recovery process.

05Preserve customer choice

Built-in providers, any compatible hosted URL and local runtimes such as Ollama or LM Studio share the same execution harness. Models become replaceable infrastructure.

06Deliver an audit trail

Tool activity, evidence, outcome state, confidence, transaction history and rollback data explain what changed, which checks ran and what remains uncertain.

Core technical thesis. Model capability will continue to converge and prices will continue to fall. The durable enterprise layer is the system that governs what models can do, verifies what they actually did and preserves operational control when models or providers change.

Capabilities

Point it at a project folder and describe what you want. It reads relevant files before changing code it hasn't seen, edits with real diffs rather than blind overwrites, and runs whatever shell commands the task needs — tests, installs, git.

Every step is narrated live, not just the final answer: a progress ring and step list track a declared plan, and a running feed shows each tool call as it happens.

✓MCP servers

✓Mobile access

01A

The complete Phases 1–13 capability stack

Wrexlyn is an execution system, not a chat wrapper. Eleven product phases combine into one controlled path from intent to inspected, reversible and evidence-backed output.

A user can ask for a feature, investigation, refactor, report, presentation or connected workflow. Wrexlyn builds context from the actual project, proposes and executes tool actions under policy, verifies what changed, records evidence, and returns an outcome that distinguishes success from uncertainty or failure.

01–02 Secure local execution foundation

Local-first runtime, authenticated web access, strict path validation, protected secret storage, SSRF-resistant fetching, scrubbed MCP environments, structured errors, dependency controls and a separated shell service. Mutating actions remain permission-gated and visibly previewed.

03 Six-state verification engine

Results are classified as verified, verified-with-warnings, unverified, failed, blocked or not-applicable. Required and advisory checks are kept distinct, so a confident model response cannot overwrite objective test evidence.

04 Complete checkpoints and rollback

Binary-safe per-file snapshots and Git-plumbing workspace checkpoints track creates, edits, deletes, renames and mode changes. Staleness checks prevent a rollback from silently overwriting newer user work.

05 Project intelligence

Lexical ranking, symbol extraction, repository structure and Git-history signals help the agent find the code that matters before editing. Search is grounded in the current project rather than depending on a model to guess filenames or architecture.

06 Evidence and consistency

Claims can cite source evidence captured during the session. The consistency layer compares facts across generated artifacts and flags contradictions, making Wrexlyn useful for diligence packs, technical reports and multi-document deliverables as well as code.

07 Professional artifact engine

A shared structured document representation compiles flowing content to Markdown, HTML and PDF while the existing Word, PowerPoint and Excel generators produce editable native outputs. Quality checks inspect the delivered structure rather than trusting a generation call.

08 Versioned skills platform

Reusable capabilities are packaged with manifests, instructions, scripts, tests and evals. Permissions are declared and previewed before a skill script can execute, turning repeatable expertise into governed product IP rather than loose prompt snippets.

09 Enterprise-grade MCP connectors

Wrexlyn supports local stdio and remote Streamable HTTP MCP servers, including OAuth 2.1 flows, per-server permission policy and anti-injection framing. External content is treated as data, not silently promoted to trusted instructions.

10 Best-of-N isolated agents

Multiple agents can attempt the same difficult task in real Git worktrees. Candidates are independently verified and ranked; the selected result can be applied without mixing intermediate edits into the user's working tree.

11 Product execution console

The desktop-grade interface brings sessions, project selection, plans, live tool activity, permission decisions, evidence, verification status and parallel-run results into one responsive workspace, with CLI parity and same-LAN mobile access.

12 Local enterprise governance

Phase 12 was intentionally redesigned to preserve Wrexlyn’s local trust model. Enterprise-grade control is applied at the customer-controlled runtime and project boundary rather than through a mandatory Wrexlyn-hosted, multi-tenant control plane. Code, prompts, credentials, policy decisions, evidence and audit data remain under customer custody; hosted LLM use is optional and replaceable.

13 Reproducible product evaluation

The evaluation layer turns product claims into repeatable system measurements across task success, verification integrity, regressions, recovery uplift, safety and cost. Runs are pinned to the Wrexlyn build, model, endpoint and task environment so harness improvement can be separated from base-model capability.

The combined advantage: project intelligence improves what the agent attempts; policy and checkpoints control how it acts; verification and evidence establish what happened; skills and connectors broaden what it can do; isolated parallel runs improve hard-task success; local governance preserves custody; reproducible evaluation proves the system’s contribution.
02

The reliability runtime

This is the actual differentiator: a deterministic control loop wrapped around the model, so answer quality doesn't depend entirely on how careful the underlying LLM happens to be.

Every mutating action — writing a file, running a command — passes through the same pipeline: it's risk-scored, gated behind permission, snapshotted before it runs, and the whole turn is checked and can be reverted afterward.

01

Risk gate

Every action is scored low / medium / high before it runs. Reading a file never prompts. Writing one does. A command matching a destructive pattern — rm -rf, git push --force, DROP TABLE — is flagged high risk and can never be pre-approved as a standing "always allow," no matter what.

02

Snapshot

Every file a mutating action touches is captured beforehand. If the turn ultimately fails verification, a single button restores every changed file to its exact prior content — no manual undo, no relying on memory of what changed.

03

Verification

After a turn that touched code, the harness runs whatever checks actually apply — typecheck, the project's real build/test/lint commands — and never invents one that isn't configured. A build failure is evidence, not a vibe.

04

Independent critic

A second, separate model call — no tools, no stake in the outcome — reviews whether the step actually did what it needed to, independent of whether it merely ran without erroring. This is what compensates for weaker or free models that won't reliably self-check.

05

Bounded repair

A failure feeds back to the model as a real, specific report, with up to three automatic repair rounds and stuck-loop detection — it stops asking the model to retry once two rounds produce byte-identical output.

06

Confidence score

Every turn ends with an evidence-based score (0–100) and outcome — verified, unverified, failed, blocked — instead of a uniformly confident tone regardless of what actually happened.

Honest about the tier of risk this addresses. The gate reduces accidental damage from a model doing something it shouldn't. It is not a sandbox — a genuinely compromised model with shell access is a different, larger problem that a permission prompt alone doesn't solve.
03

Document generation

Word, PowerPoint, and Excel output as real, structured files — not write_file pretending to be a document generator. Formatting is a first-class input, not an afterthought:

Word

Inline bold/italic/underline/strike, numbered & nested lists, real images sized from their own aspect ratio, a genuine auto-updating table of contents, per-cell table formatting, custom accent color.

PowerPoint

Section-divider and two-column layouts, in-slide tables and images, nested bullets — and deliberately no decorative accent-stripe under every title, the single most recognizable tell of an AI-generated deck.

Excel

Live, recalculating formulas rather than baked-in numbers, per-column currency/percent/date formats, merged cells, autofilter.

Every one of these was verified by unzipping the actual generated file and asserting on its real OOXML — bold runs present, numbering XML present, image relationships registered — not just "the call didn't throw."

04

Architecture

One Node.js process, no bundler for the frontend, no external services required. The browser UI talks to it over a single WebSocket; every tool call, permission prompt, and streamed token flows through that same typed protocol.

LayerWhat it is
Agent loopDrives the model, dispatches tool calls, runs the reliability pipeline described in §02, persists sessions to disk per project.
ToolsFile read/write/edit, glob/grep, shell exec, Word/PowerPoint/Excel/PDF generation & reading, web fetch — each with its own risk classification.
Provider layerA shared OpenAI-compatible HTTP/SSE client backs the integrated providers and the user-configured Custom / Local Model option. Entering a base URL, model name and optional API key lets Wrexlyn use a hosted endpoint or a locally running server while preserving streaming, tool calling, retry behavior and the same verification runtime.
Web serverStatic file serving (no build step — edits to the UI are live on refresh) plus the WebSocket protocol and a handful of local-only REST endpoints (file browsing, model lists, LAN QR code).
PersistencePer-project sessions, transaction/audit log, learned preferences, and saved skills under .coding-agent/; machine-wide settings (API keys, global instructions) under the user's home directory.

Requests are also kept lean on purpose: a round where every action already passed its own document quality gate (§12) skips the independent-critic call for that round rather than spending a second model round-trip to catch a class of mistake the deterministic check already caught for free — fewer requests per turn, and fewer 429s as a direct result.

07

Web demo

A separate, deliberately scoped-down build: a static page hosted on GitHub Pages, sign in with Google, bring your own key, and chat — with an honest ceiling on what a static page can do.

No file or shell tools — a browser sandbox genuinely cannot run code on a visitor's machine, GitHub Pages or not. Google Sign-In is client-side only and nothing about who's signed in is stored anywhere. An entered API key is kept in that browser's local storage and sent directly from the browser to the chosen provider — this page never sees it.

What the demo deliberately keeps: the same provider dispatch and retry logic as the full agent, so a rate-limited or slow provider behaves identically to how it behaves in the desktop build, and the same streaming response rendering. What it deliberately drops: the entire reliability runtime in §02 (no filesystem to snapshot, no build to run), the document quality gate in §12 (no file to write to disk), and the persistence in §13 (no server-side project to remember preferences against) — because none of those have a coherent meaning without a local project and a local filesystem behind them. It exists to let someone evaluate the model conversation itself in under a minute, not to be a lighter version of the real tool.

08

Security & privacy

Data residencyEverything — code, sessions, generated files, API keys — stays on the machine running the agent. Nothing is sent anywhere except the model provider you chose, for the messages you sent it.
Sandbox boundaryFile tools are confined to the chosen project root; a path that resolves outside it is rejected before touching disk.
Key storageProvider credentials are stored through the platform-aware secret store, with restrictive local-file fallback behavior where an operating-system credential facility is unavailable.
Shell executionCommands are delegated to a separated shell-execution service, constrained to the selected workspace and gated by the risk and permission system in §02. This limits process coupling, but is not a container or virtual-machine security boundary.
Learned dataPreferences and saved skills (§13) are written to plain local files under the project or the user's home directory, never to a remote service — the same residency guarantee as sessions and generated documents.
UndoEvery mutating action is snapshotted (§02) before it runs, so a bad turn — code or document — can be reverted to its exact prior state with one action, without relying on a separate backup.
08A

Evaluation and proof standard

A serious coding agent must be evaluated as a complete system, not by showing that its model can produce plausible code. Wrexlyn separates base-model ability from the measurable contribution of its context, governance, verification and recovery layers.

A reproducible evaluation pins the Wrexlyn commit, model and version, endpoint configuration, repository or container image, task definition and verification command. It retains tool traces, diffs, outcome states, repair rounds, token usage, wall time and grader output. Results should be reported by model tier so a frontier model does not hide a weak harness and a low-cost model does not hide a strong one.

Current evidence boundary. The product contains the architecture required to run these evaluations and automated tests covering its internal mechanisms. The 81/100 peer score is an analyst capability/readiness assessment, not task accuracy. Wrexlyn should claim leaderboard performance only after model-pinned runs on official, unmodified harnesses are published with reproducible traces.

Recommended external sequence: start with a private 25-task customer pilot; publish same-model ablations on recovery and verification; then run SWE-bench Verified, Terminal-Bench 2, BFCL and economically grounded task sets such as SWE-Lancer. This order establishes customer value before spending heavily on broad leaderboard coverage.

Roadmap

Known gaps, tracked rather than hidden — the same honesty this document tries to apply to everything else it describes.

Sandboxed execution

Container-level isolation for shell commands, for the small set of use cases where host-level trust isn't acceptable.

Mid-flight cancel

A cancel affordance for a long-running tool call, rather than waiting it out.

Optional customer-controlled coordination

Where organizations require shared policy or team administration, coordination should remain customer-hosted or explicitly opt-in. A mandatory Wrexlyn cloud control plane is intentionally outside the local-first product contract.

Cross-session search

Semantic search across past sessions, beyond the current recency-grouped list.

Prose-quality scoring

The §12 quality gate is deterministic and structural by design; a genuinely writing-quality-aware check would need its own model call, with its own cost and reliability trade-offs, and hasn't been added yet.

Shared/team skills

§13 skills are per-project today; a way to promote one to a team-shared library is a natural next step, not yet built.

11

Why the skills library is differentiated

Most quantitative screening in these sectors runs on an analyst’s gut-check translated into a number that means something different depending on who’s asking and when. These 14 algorithms replace that with named, versioned frameworks built to one shared design discipline — not 14 unrelated one-off scoring hacks.

✓Named & versioned

“NDQI 74” means the same thing regardless of who is asking or answering, this year or next — in the tradition of other analyst-attributed models like the Altman Z-Score.

✓Deliberate, not arbitrary

Every pillar’s weight reflects a stated view of what actually drives outcomes in that domain — entry price and trajectory dominate PE screening; clinical-stage probability of success dominates drug-pipeline triage.

✓Auditable, not a black box

Missing data degrades a confidence rating instead of being silently guessed, and every score ships with a runnable reference implementation — the claim is checkable, not just quotable.

The full methodology — formulas, worked examples, and an honest IP-defensibility read — is documented as a trade secret and kept private; it’s available for review under NDA, not published here.

12

Document quality gate

A generated document is a claim the model makes about its own work. The reliability runtime in §02 verifies code by running it; a .docx/.pptx/.xlsx can’t be "run" the same way, so a separate, deterministic checker inspects the file itself — structurally, not by asking a second model whether it looks right.

01

Structural checks, not a model opinion

Leftover placeholder text (TODO, lorem ipsum, [insert…, TBD), a table row whose length doesn’t match its header, a table or sheet with headers but zero data rows — each is plain code inspecting the actual blocks/slides/sheets about to be written, not an LLM asked to grade its own homework.

02

Fails closed, before the file is written

A blocking check runs immediately before create_docx/create_pptx/create_xlsx commits the file to disk. On failure the tool call returns a specific reason instead of a corrupted or half-finished document, and the model retries in the same turn — the same closed-loop-retry pattern §02 uses for code, applied to documents.

03

Non-blocking warnings for softer issues

A slide with more than six bullets, a paragraph over ~150 words with no inline formatting in an otherwise-formatted document, a numeric-looking spreadsheet column with no number format — these are reported alongside a successful result rather than blocking it, the same warning-not-error pattern already used for the §03 Excel merged-cell checks.

04

Confidence scoring stops flattening document turns

A document-only turn used to be capped at a flat 60% confidence and an "unverified changes" outcome no matter how clean the output actually was, because nothing had checked it. A turn where every document action passed this gate is now scored as genuinely verified — the confidence number reflects what was actually checked, not just what category of action ran.

What this can and can’t fix. This is real irrespective of which integrated, custom or local model wrote the document — a weak model’s placeholder text or empty section gets caught and forced to retry every time, exactly as reliably as a frontier model’s would be. It cannot upgrade a weak model’s prose quality to a strong model’s; no deterministic checker can judge writing quality. What it guarantees is structural: no placeholder text, no jagged tables, no silently empty sections reach you.
13

Self-learning

Most assistants forget everything the moment the session ends. A stated preference or a hard-won lesson from a mistake earlier in the conversation should not have to be repeated — and it shouldn’t require Wrexlyn to rewrite its own source code to remember it.

✓Remembers stated preferences

A remember_preference tool call persists a standing instruction — formatting, tone, workflow — either project-scoped (into that project’s own memory) or global (into a machine-wide instructions file), the moment the user states it, not just for the current turn.

✓Saves reusable skills

A save_skill call persists a genuinely reusable multi-step pattern to disk under .coding-agent/skills/. Every saved skill’s name and description load into the system prompt on the next session; recall_skill fetches its full steps on demand, keeping the prompt itself small.

✓Applies immediately, not next session

Learning a preference or a lesson rebuilds the system prompt in place, in the same turn — a preference stated mid-conversation governs the very next response, rather than only taking effect the next time the project is opened.

This is deliberately scoped to memory and prompts, not code. Wrexlyn never edits its own shipped source autonomously in response to a mistake — a genuine code-level bug is fixed the way any real bug is: as a normal, permission-gated, reviewed, and verified change. Only the safe part — what to remember, what to prefer, what pattern worked — is automatic.

14

The Nishant Convergence Protocol

A weak or free model is rarely bad at writing a first attempt. It is bad at self-correcting when that attempt fails — given a generic “fix the root cause and try again,” it disproportionately repeats a near-identical change or thrashes to something unrelated. The Nishant Convergence Protocol (NCP) targets exactly that moment, formalized as a named, versioned, unit-tested algorithm (src/convergence.ts) rather than a loose heuristic.

Said plainly, upfront: NCP does not make a small model reason like a large one. No runtime layer manufactures capability the underlying weights don’t have. What it closes is the reliability gap on tasks with an external check — a build, a test, a structural document rule — the same category §02’s reliability runtime already operates on. It is the mechanism that makes that runtime’s repair step measurably smarter, not a claim of raw intelligence uplift.

01

Divergent diagnosis ensemble

Once a plain repair attempt has already failed once, two independently-framed root-cause diagnoses are generated in parallel from the same failure evidence — one biased toward the obvious cause, one explicitly asked to look past it for a side effect or stale assumption.

02

Pairwise adjudication

A dedicated comparative call judges the two diagnoses against each other rather than scoring either in isolation — a measurably more reliable judgment for an LLM to make — and returns a winner plus a margin: clear or close.

03

Lesson-steered regeneration

The project’s learned lessons (§13) are ranked by keyword-overlap relevance to the current failure and foregrounded directly inside both diagnosis prompts as explicit constraints — the first mechanism to actively retrieve self-learned lessons rather than leave them as passive system-prompt context.

04

Formalized convergence score

ConvergenceScore = clamp(0, 100, OutcomeBase − 6×RepairRounds + 8×[clear NCP win] − 15×[known failure recurred]). On the common case — zero repair rounds, NCP never invoked — this returns the existing outcome-based score completely unchanged; it’s a strict refinement, not a replacement.

Adaptive, not blanket. The ensemble only engages once a first, single-shot repair attempt has already failed (repair attempt 2 of the existing 3-round ceiling). Most repairs succeed on the first try; spending three extra model calls on every one of them would be a direct cost and rate-limit regression, working against the retry/backoff efficiency work described elsewhere in this document. NCP spends its extra compute only once a turn has already proven itself stuck — exactly where the marginal value of a second opinion is highest and the frequency of that moment is naturally low.

All four pure functions underlying NCP — the relevance ranker, the recurrence check, the score formula, and the ensemble orchestrator itself — are covered by unit tests against a mocked model backend, including the fail-open path when a provider is unavailable. Full methodology, formal scoring derivation, and the acquisition-relevant IP framing are documented separately as a private technical whitepaper, available for review under NDA.

Competitive positioning

Four categories of tool currently answer “how do I get an AI to write my code,” and each optimizes for something Wrexlyn deliberately does not trade away to get. This is a map of the actual trade-off, not a claim that the other categories are bad at what they optimize for.

CategoryWhat it optimizes forWhat you give upWhere Wrexlyn sits
Inline autocomplete assistantsSpeed of a single suggestion, in-editorNo multi-file planning, no verification loop, no memory across sessionsA full agent loop with its own risk-gating and repair — a different tier of task, not a faster version of the same one
IDE-embedded agentic assistantsConvenience — one tool, one subscription, tied to a specific editorUsually a fixed model, usually a subscription regardless of which free tiers exist upstreamEditor-agnostic with integrated providers, arbitrary compatible URLs and local model servers (§05)
Hosted autonomous SaaS agentsFire-and-forget delegation — describe the task, walk awayYour code and prompts leave your machine; verification, if any, happens on infrastructure you can't inspectRuns locally; every risk gate, checkpoint and verification result remains inside the customer's controlled environment
Other local/terminal agentsAlso local, also model-agnostic in the better ones — the closest real comparisonTypically no independent critique step, no formalized confidence score, no structural gate on generated documentsV-Cycle’s independent critic (§02), the document quality gate (§12), and the Nishant Convergence Protocol (§14) are the specific, checkable things that differ, not a general claim of being “better”

The honest version of this pitch is narrower than “better at everything”: Wrexlyn's actual bet is that verified reliability compounds where raw generation speed does not. A tool that is 20% slower per turn but catches its own mistakes before calling a turn done, remembers what you told it, and gets measurably better at repairing itself over the course of a project, ends up costing less real time than one that is fast per turn and wrong an unflagged fraction of them — especially once free/lower-cost models, not always the frontier ones, are doing the generating.

✓Evidence, not claims

Every mechanism cited on this page — retry/backoff behavior, verification outcomes, checkpoints, evidence handling and document quality controls — is backed by automated tests in the proprietary product codebase. A claim supported by reproducible checks is a different kind of claim than one supported only by marketing copy.

✓Named, versioned mechanisms

“The V-Cycle runtime,” “the document quality gate,” “the Nishant Convergence Protocol” are specific, citable names for specific pieces of code — not a marketing umbrella over whatever the model happened to do that day.

✓Disclosed limits, not just wins

Every differentiation claim on this page has a matching “honest scope” callout stating what it does not do — §02's sandbox disclaimer, §14's capability-vs-reliability distinction. A tool that discloses its own ceiling is more trustworthy at the claims it does make, not less.
